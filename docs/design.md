## 1. Problem statement
Inbound shipment delays are costly and hard to diagnose after the fact. Planning teams currently review delays manually, which is slow and doesn't scale as shipment volume grows. This project analyzes historical shipment data to identify the top drivers of delay and predicts delay risk before shipment, so planners can intervene early instead of reacting after a shipment is already late.

## 2. Who will use it
An inbound logistics planning manager who currently spends hours each week manually reviewing delayed shipments to figure out patterns, and who wants a faster, evidence-backed way to know which carriers, routes, or conditions are driving delays this week.

## 3. Scope
**In scope:**
- Predicting whether a shipment will be late (binary: late / not late)
- Identifying the top delay drivers with supporting evidence
- An interactive dashboard for drill-down analysis
- An automated weekly written summary generated by an AI agent

**NOT in scope:**
- Predicting exactly how many days late a shipment will be — the dataset isn't granular enough to support that reliably
- Real-time/live shipment tracking — this is a weekly-batch analysis tool, not a live ops system

## 6. Success metrics
- Model: PR-AUC on a time-split test set, beating a naive "always predict on-time" baseline
- Root cause: at least 3 delay drivers identified with clear supporting evidence (charts/stats, not guesses)
- Reporting: an AI-generated weekly summary that accurately reflects the computed numbers, with zero invented statistics
- Dashboard: published and publicly viewable via link in the README

## 7. Risks
- **Data leakage**: features that wouldn't be known at ship-time (e.g.
  actual delivery date) must not be used to predict lateness.
- **Class imbalance**: most shipments are probably on-time, so accuracy
  is a misleading metric — use PR-AUC/recall instead.
- **AI hallucination**: the LLM must only summarize numbers you already
  computed — it must never be asked to calculate or invent a statistic.
